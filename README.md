## 📌 Overview

Modern infrastructure generates thousands of log lines per second. During incidents, engineers manually grep through stack traces, cross-reference documentation, and piece together root causes under pressure — a process that is time-consuming, error-prone, and fundamentally unscalable.

**AI DevOps Log Analyzer** is a production-oriented multi-agent AI system that automates the entire incident analysis pipeline. It reads raw logs, identifies failure patterns, investigates issues against real-world knowledge sources, and delivers confidence-scored, actionable remediation plans — without a human in the loop.

This is not a toy demo. It is an end-to-end reasoning system built around the principle that **the most expensive part of an incident is not the failure itself — it is the time engineers spend diagnosing it.**

### What it solves

| Without This System | With This System |
|---|---|
| Engineer manually reads 5,000 log lines | Parser extracts critical events in seconds |
| Cross-references Stack Overflow, docs, GitHub issues by hand | EXA agent searches authoritative sources automatically |
| Solution quality depends on engineer's experience level | Structured remediation plan with confidence score |
| Incident diagnosis: 45 min – 4 hours | First analysis pass: under 3 minutes |

## 💡 Motivation & Inspiration

The idea for this project came from a frustration familiar to anyone who has been on-call: **the gap between knowing something is broken and knowing exactly why.**

Three converging trends made this the right moment to build it.

**1. The scale problem is unsolvable by hand.** Microservices architectures, containerized deployments, and distributed systems have made log volumes unmanageable for manual analysis. Teams need systems that can reason about logs, not just search them.

**2. AI agents are now capable of real engineering work.** Frameworks like CrewAI enable coordination between specialized agents — each with distinct roles, tools, and reasoning contexts. The gap between "AI that answers questions" and "AI that investigates problems" has closed enough to build production systems on.

**3. Real-time knowledge retrieval changes the equation.** Tools like EXA Search allow agents to ground their analysis in current documentation, recent GitHub issues, and community knowledge — not just frozen training data. This is the difference between a model that hallucinates a fix and one that cites a PostgreSQL changelog entry.

The goal was to build something that a real DevOps team could point at a log file and trust.

### Agent Deep Dive

#### 🔍 Agent 1 — Log Analyzer Agent

The entry point of the pipeline. Transforms raw, unstructured log output into a structured failure summary that downstream agents can reason about efficiently.

- Reads log files via the custom `log_reader_tool`
- Identifies error signatures, exception types, and failure frequencies
- Tags events by severity: `CRITICAL` / `ERROR` / `WARNING` / `INFO`
- Detects temporal patterns (e.g., errors clustering at 09:47, recurring every 15 minutes)
- **Hard constraint:** Operates exclusively on data present in the log file — no external assumptions permitted

#### 🌐 Agent 2 — Issue Investigator Agent

Takes the structured failure report from Agent 1 and performs evidence-based research using EXA Search. Bridges the gap between "what happened" and "why it happens."

- Queries EXA for known issues matching identified error signatures
- Searches across GitHub issues, official documentation, CVE databases, and community forums
- Returns cited source URLs alongside every finding — speculation without evidence is explicitly disallowed in the task prompt
- Filters low-authority sources and surfaces the most relevant, up-to-date information

#### 🛠️ Agent 3 — Solution Specialist Agent

The synthesis layer. Consumes outputs from both upstream agents and generates a structured remediation plan an on-call engineer can act on immediately.

- Maps investigated root causes to concrete, environment-specific fix strategies
- Generates production-ready commands with exact flags, paths, and version qualifiers
- Assigns a **confidence score (0–100%)** to each recommendation with explicit justification
- Distinguishes between immediate mitigation, short-term fix, and long-term architectural improvement
- Flags situations that require human escalation

## 🚀 Development Journey

> *This section documents the full engineering story — from a single-agent proof of concept to a three-agent production system. Every architectural decision reflects a real constraint, failure, or insight encountered during development.*

---

### Phase 1 — Proof of Concept

The project started with a deliberately minimal question: *Can an LLM reliably extract actionable information from messy, real-world log files?*

The first prototype was a single CrewAI agent, no external tools, receiving a hardcoded log string directly inside the task description. The goal was not functionality — it was validation. Can the model distinguish an `INFO` line from a `CRITICAL` failure? Does it recognize common error signatures?

The answer was **yes, conditionally.** Standard patterns — HTTP 5xx codes, Python tracebacks, database connection errors — were handled well. Custom formats and domain-specific error codes were not. This surfaced a fundamental design requirement early: **the LLM needed pre-structured input, not thousands of raw log lines.**

First architecture:

```
Raw Log String (hardcoded) → Single LLM Agent → Unstructured Text Output
```

Functional for a demo. Useless in production. But the concept was proven.

---

### Phase 2 — Building Real Infrastructure

**Custom Log Parser (`log_analyzer.py`):** The highest-impact early addition. A regex-based module that pre-processes raw logs before they reach the agent layer. It extracts error signatures, tags severity levels, identifies temporal patterns, and returns a structured Python dictionary. This reduced token consumption significantly and dramatically improved analysis quality — the model received labeled, organized data instead of raw noise.

**Multi-Agent Pipeline:** The single-agent architecture was replaced with the three-agent sequential pipeline. The core insight: *parsing what happened*, *researching why it happens*, and *prescribing how to fix it* are fundamentally different reasoning tasks. Combining them in one agent produced shallow outputs across all three. Separating them produced deep, high-quality outputs in each.

**EXA Search Integration:** The most significant capability addition. The Issue Investigator gained access to real-time web search, grounding analysis in current documentation rather than frozen training data. For infrastructure issues where a library bug may have been patched three weeks ago and the fix is only in a GitHub PR comment, this is the difference between a useful recommendation and a stale one.

---

### Phase 3 — Prompt Engineering and Reliability

The pipeline worked. Outputs were not yet consistently trustworthy.

**Hallucination problem:** Without explicit constraints, the Investigator agent occasionally cited plausible-sounding references that did not exist. Fix: task descriptions were updated to require source URLs for every claim, and the Solution Specialist was instructed to flag any recommendation not traceable to a cited source.

**Generic solutions problem:** Early output read like Stack Overflow answers — accurate but not actionable for a specific environment. Fix: backstory engineering. The Solution Specialist's persona was rewritten from "You are an expert DevOps engineer" to a precisely scoped senior SRE persona with explicit constraints against general advice, speculation, and recommendations without version-specific details. Output quality improved immediately and substantially.

**Confidence scoring** was added as a direct reliability mechanism — requiring a percentage and justification forces meta-cognitive reflection that measurably reduces overconfident incorrect answers.

## 🐛 Challenges & How They Were Solved

> *This section is not a list of minor inconveniences. These are real engineering problems that blocked progress and required systematic debugging to resolve. If you are building with this stack, read this before you start.*

---

### Challenge 1 — `crewai.llm` Module Not Found

**Error:**
```
ImportError: cannot import name 'LLM' from 'crewai'
```

**Root cause:** The `LLM` class migrated between module paths across CrewAI minor versions. Direct `from crewai import LLM` worked on some builds and silently failed on others.

**Resolution:**
```python
# ❌ Unstable across versions
from crewai import LLM

# ✅ Explicit path — stable
from crewai.llm import LLM
```

Combined with: `crewai==0.30.11` pinned in `requirements.txt`.

---

### Challenge 2 — OpenRouter API Key Confusion

**Error:**
```
AuthenticationError: No API key provided.
```

**Root cause:** CrewAI delegates LLM calls to LiteLLM, which reads `OPENAI_API_KEY` and `OPENAI_API_BASE` regardless of the actual provider. Setting `OPENROUTER_API_KEY` in `.env` does nothing — it is silently ignored.

**Resolution:**
```env
# .env — correct variable names for OpenRouter via LiteLLM
OPENAI_API_KEY=sk-or-v1-your-openrouter-key-here
OPENAI_API_BASE=https://openrouter.ai/api/v1
```

```python
# agents.py
from crewai.llm import LLM
import os

llm = LLM(
    model="openai/gpt-4o",
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_API_BASE"),
)
```

---

### Challenge 3 — `.env` File Not Loading

**Symptom:** Environment variables returned `None` despite correct `.env` contents. API calls failed silently.

**Root cause:** `load_dotenv()` was called *after* modules that consumed those variables were imported. Python reads module-level code at import time — variables were evaluated before `load_dotenv()` ran.

**Resolution:**
```python
# main.py — load_dotenv() must be the first statement executed
from dotenv import load_dotenv
load_dotenv()  # ← must precede all project imports

import os
from agents import create_agents   # ← only after .env is populated
from tasks import create_tasks
```

---

### Challenge 4 — `@tool` Decorator Breaking Agent Initialization

**Error:**
```
pydantic_core._pydantic_core.ValidationError: tools
  Value error, tools must contain instances of BaseTool or their subclasses.
```

**Root cause:** The `@tool` decorator's return type changed between CrewAI versions. Passing the decorated function directly failed Pydantic v2 validation unpredictably.

**Resolution:** Replaced `@tool` functions with explicit `BaseTool` subclasses — stable across all Pydantic v2 builds:

```python
# tools.py
from crewai.tools import BaseTool
from pydantic import BaseModel, Field
from typing import Type

class LogReaderInput(BaseModel):
    file_path: str = Field(description="Path to the log file to read")

class LogReaderTool(BaseTool):
    name: str = "Log File Reader"
    description: str = "Reads a log file from disk and returns its full contents"
    args_schema: Type[BaseModel] = LogReaderInput

    def _run(self, file_path: str) -> str:
        try:
            with open(file_path, "r", encoding="utf-8") as f:
                return f.read()
        except FileNotFoundError:
            return f"ERROR: File not found at '{file_path}'"
        except PermissionError:
            return f"ERROR: Permission denied reading '{file_path}'"
```

---

### Challenge 5 — EXA SDK Class Rename

**Error:**
```
ImportError: cannot import name 'EXA' from 'exa_py'
```

**Root cause:** The EXA Python SDK renamed its class from `EXA` to `Exa` in `exa_py==1.0.0`. No deprecation warning — a hard import failure.

**Resolution:**
```python
# ✅ Correct for exa_py >= 1.0.0
from exa_py import Exa
exa_client = Exa(api_key=os.getenv("EXA_API_KEY"))
```

Pinned: `exa_py==1.1.0`

---

### Challenge 6 — Pydantic v1 / v2 Conflict

**Error:**
```
langchain-core 0.1.52 requires pydantic>=1,<3
crewai 0.30.11 requires pydantic>=2.4.2
```

**Symptom:** Mixed Pydantic versions caused silent runtime validation failures mid-pipeline — no error at startup, failure during agent execution.

**Resolution:** Full dependency audit with explicit pinning:

```
crewai==0.30.11
langchain-core==0.2.10
langchain==0.2.5
pydantic==2.7.1
litellm==1.39.1
```

> **Core lesson:** In AI framework projects, treat `requirements.txt` as a lockfile. Version ranges are a maintenance liability in a space where minor bumps routinely introduce breaking API changes.

## ⚙️ Setup & Installation

### Prerequisites

- Python 3.10 or higher
- [OpenRouter](https://openrouter.ai) account and API key
- [EXA Search](https://exa.ai) account and API key

### 1. Clone the Repository

```bash
git clone https://github.com/yourusername/ai-devops-log-analyzer.git
cd ai-devops-log-analyzer
```

### 2. Create a Virtual Environment

```bash
python -m venv venv

# Linux / macOS
source venv/bin/activate

# Windows
venv\Scripts\activate
```

### 3. Install Pinned Dependencies

```bash
pip install -r requirements.txt
```

> ⚠️ **Do not** run `pip install crewai` without the version pin. See [Challenges](#-challenges--how-they-were-solved) for why unpinned installs are the primary source of runtime failures in this stack.

### 4. Configure Environment Variables

```bash
cp .env.example .env
```

Edit `.env`:

```env
# ────────────────────────────────────────────────────────────
# OpenRouter Configuration
#
# IMPORTANT: CrewAI uses LiteLLM internally, which reads from
# OPENAI_API_KEY regardless of the actual provider. This is
# not a typo — use exactly these variable names for OpenRouter.
# ────────────────────────────────────────────────────────────
OPENAI_API_KEY=sk-or-v1-your-openrouter-api-key-here
OPENAI_API_BASE=https://openrouter.ai/api/v1
MODEL_NAME=openai/gpt-4o

# ────────────────────────────────────────────────────────────
# EXA Search
# ────────────────────────────────────────────────────────────
EXA_API_KEY=your-exa-api-key-here
```

### 5. Add Your Log File

```bash
cp /path/to/your/system.log logs/target.log
```

Update the file path in `main.py` if needed (default: `logs/target.log`).

### 6. Run the Analyzer

```bash
python main.py
```

Progress is printed to stdout as the pipeline advances through each agent phase. The completed report is written to `outputs/analysis_report.md`.

**Expected runtime:** 45 seconds – 3 minutes, depending on log size and LLM latency.

## 🎯 Why This Project Stands Out

Most AI portfolio projects demonstrate that an engineer can call an API. This one demonstrates something different.

**It solves a real, costly problem.** Incident diagnosis is one of the most expensive activities in software operations. Automating even part of it has direct, measurable business value — not hypothetical value.

**It shows system thinking, not just code.** The separation of analysis, investigation, and remediation into distinct agents reflects a deliberate architectural decision, not convenience. Each component has a defined scope, a reasoning constraint, and a quality mechanism.

**It confronts the reliability problem honestly.** The Challenges section documents real failure modes and real fixes. Anyone who has built with these frameworks knows how hard dependency management is in this space. Documenting it demonstrates engineering maturity.

**It combines three distinct domains.** AI agent orchestration, DevOps/SRE practice, and real-time knowledge retrieval are each non-trivial fields. Building a coherent, working system across all three requires genuine understanding of each.

**It is architecturally extensible.** The modular design means the system is not tied to any specific LLM, log format, or tool. Adding a new agent, swapping the search provider, or integrating a new log source requires changes to a single, well-scoped file.
